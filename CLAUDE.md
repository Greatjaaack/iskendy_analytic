# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Что это

Система аналитики и учёта костов ресторана «Искенди» (storeId `161059`). Продажи тянутся с кассы через **порт `backend/pos/`** (сейчас провайдер iiko — внутренний, нереверс-инженерный API iikoweb `https://iskendi.iikoweb.ru`; готов адаптер Saby Presto, см. `SABY_API.md`) и отдаются фронту через FastAPI. Сверх дашборда ведётся **собственная БД** поставщиков, цен, тех-карт (ТТК) и себестоимости — **в iiko ничего не пишем, только читаем**. Справочник эндпоинтов/метрик iikoweb — в `IIKO_WEB_API.md`; дорожная карта — `PLAN.md`; журнал работ — `PROGRESS.md` (читать перед работой с API/планированием).

## Команды

Запуск в Docker (рекомендуется): `docker compose up -d --build`. Frontend на http://localhost:5173 (nginx, проксирует `/api` на backend), backend на http://localhost:8000. БД живёт в volume `backend-data`. Нужен заполненный `.env` в корне (его читает `env_file`); `DATABASE_URL` в контейнере переопределяется на `/data/iskendi.db`. Логи: `docker compose logs -f backend`.

Запуск локально без Docker: `./start.sh` (ставит зависимости, ставит chromium для Playwright, поднимает backend на :8000 и frontend на :5173).

Backend (из `backend/`):
- `pip install -r requirements.txt && python -m playwright install chromium`
- `uvicorn main:app --reload --port 8000`
- Триггер ручной синхронизации: `POST /api/sync`; здоровье: `GET /api/health`.
- Тесты: `pip install -r requirements-dev.txt && python -m pytest tests/ -q` — **170 тестов**. Общая обвязка в `tests/conftest.py`: фикстурная БД на 14 дней (повторяющиеся номера заказов, «Статус», модификатор, сплит-оплата, ТТК с привязкой), погода из словаря и **касса-заглушка, падающая при любом обращении** — так смоук доказывает, что ручки за период внутри истории читают БД, а не кассу. `tests/test_smoke_api.py` прогоняет **каждую** читающую ручку и сверяет **инварианты** (число чеков одинаково во всех разрезах, Σ по часам/каналам/дейпартам/оплатам = выручке, P&L и ОП-отчёт берут ту же выручку); `test_все_ручки_покрыты` сверяется с OpenAPI, поэтому новая ручка без теста валит сборку. Остальные файлы: `test_orders_today.py`/`test_summary.py` (контракты ручек табло), `test_order_key.py` (ключ заказа), `test_revenue_source.py` (источник дней и час закрытия), `test_security.py` (защита ручек), `test_sync_guards.py` (предохранители синка), `test_housekeeping.py` (уборка), `test_db_runtime.py` (режим SQLite), `test_pos_iiko.py`/`test_pos_saby.py` (адаптеры кассы), `test_logging.py` (отсев шума в логе, статусы `sync_log`, частота проверки сессии iiko).

Frontend (из `frontend/`):

Код-стайл: см. `code-style.md` (корень). Backend приведён к нему (`black`/`isort`/`flake8`/`mypy`,
конфиг в `backend/pyproject.toml` и `backend/.flake8`, line-length 100). Перед коммитом:

## Архитектура

Поток данных: **касса → адаптер в `backend/pos/` → `scheduler` синкает ВСЁ в SQLite (выручка по дням + заказы на уровне позиций) → роутеры читают из БД → React-фронт**. Живые запросы к iiko делает **только планировщик** (фоновый синк + бэкафилл всей истории); на пути запроса дашборда живой iiko остаётся лишь как **fallback** для диапазонов старше начала сохранённой истории. Косты/ТТК/поставщики — из собственной БД (наполняется импортом xlsx).

### Авторизация в iikoweb (ключевой нюанс)
`backend/iiko_web_client.py` — внутренний API защищён cookie-сессией (TTL ~20 мин), отдельного login-endpoint нет. `_login()` поднимает **headless Chromium через Playwright**, вводит логин/пароль как человек на странице `/navigator/index.html#/auth/login`, забирает cookies и дальше шлёт быстрые JSON-запросы через `httpx` с этими куками. `_ensure_session()` проверяет сессию через `/api/auth` и перелогинивается при истечении; `_post()` при 401/403 сбрасывает куки и повторяет один раз. Пароль — только в `.env`.

### Защита ручек (этап 4 аудита, 25.09.2026)
**Перебор пароля** — `backend/ratelimit.py`: скользящее окно на минуту по IP,
`LOGIN_LIMIT` = 10 попыток, ответ 429; адрес берётся из `X-Forwarded-For` только если
запрос пришёл из приватной сети (то есть от нашего прокси), иначе заголовок можно было бы
подделать. **Сверка секретов — по байтам** через `hmac.compare_digest`: логин/пароль
(`auth.verify_credentials`; на строках падал `TypeError` → 500 вместо 401 при кириллице) и
internal-токен (`main._require_internal`; обычное `!=` сравнивает до первого различия).
**Загрузка файлов** — `storage.save_upload`: пишется кусками, обрывается на
`MAX_UPLOAD_MB` (413) и принимает только `storage.ALLOWED_EXTENSIONS` (415); недописанный
файл удаляется. Раньше `await file.read()` тянул файл целиком в память при `mem_limit:
512m`. **Тела write-ручек — pydantic-схемы** (`plan`, `pnl/costs`, `pnl/day-costs`,
`schedule/employees` ×2, `schedule/shifts/toggle`): было `payload: dict`, и запрос без
обязательного поля падал 500 в глубине кода. `Literal` в схемах совпадает со
справочниками роутера — это проверяет тест. **CORS** — только `CORS_ORIGINS` (по умолчанию
localhost для dev; на проде фронт и API за одним адресом, CORS не участвует), было `*`.

### Авторизация дашборда (логин/пароль)
Весь дашборд закрыт за экраном входа. **Бэкенд** (`backend/auth.py`): один общий логин/пароль из `.env` (`AUTH_USERNAME`/`AUTH_PASSWORD`; пустой пароль = вход выключен, сверка в константное время через `hmac.compare_digest`). Сессия — **JWT (HS256), подписан вручную на `hmac`** (без внешних зависимостей), TTL `JWT_TTL_HOURS` (дефолт 12 ч); секрет подписи — `JWT_SECRET`, при пустом выводится из пароля (`iskendy:<auth_password>`). Роутер `backend/routers/auth.py`: `POST /api/auth/login` (логин/пароль → `{token, username}`), `GET /api/auth/me` (проверка токена). Зависимость **`require_auth`** (Bearer-JWT, иначе 401) навешена в `main.py` на **все роутеры и `/api/sync*`**; публичны только `/api/health` и `/api/auth/login`. **Фронт**: токен в localStorage (`src/token.ts`), axios-перехватчики (`src/api.ts`) добавляют `Authorization: Bearer` и при 401 чистят токен + редиректят на `/login`; guard `RequireAuth` (`src/auth.tsx`) оборачивает защищённые роуты в `App.tsx`; экран входа — `src/pages/Login.tsx`; кнопка «Выйти» — в `Sidebar`. Это **локальная авторизация дашборда**, не путать с cookie-сессией iikoweb выше.

### Единый эндпоинт данных
Почти все метрики идут через один вызов `POST /api/kpi/dashboard/get-data` (`get_metrics()`), параметризованный `metricCodes` + `dataType` (`DATA_SUMMARY_BY_DATE` для выручки по дням, `DATA_DETAILS` для блюд, `DATA_TOTAL` для итогов). Названия и категории блюд приходят **в том же ответе** в блоке `decoration.product` (с `with_decoration=True`) — отдельного справочника блюд не нужно. Коды метрик — выручка через `REV_GROSS` (бухгалтерские `ACC_CAT_*`/НДС в этой точке возвращают 0, не использовать).

**Healthcheck** в обоих compose-файлах (`curl /api/health`, интервал 60 с, `start_period`
120 с — старт небыстрый из-за синка): состояние видно в `docker ps`. Docker по нему
контейнер **не перезапускает** — это делает сторож. **Сторож `guard.sh`** (в репозитории
табло, крон каждые 5 минут) с 25.09.2026 проверяет и аналитику: `https://analytics.iskendy.ru/api/health`
через локальный резолв, при двух промахах — `docker restart dashboards-backend-1`, затем
сообщение в тему аварий. Зачем: табло тянет заказы из `/api/orders/today`, и падение
аналитики останавливает заказы на экране гостя, тогда как сам сайт отвечает 200 — раньше
это приходилось замечать вручную.

### Журнал (`backend/log_setup.py`)
Замер на проде 26.09.2026: 2 196 строк в час, ~90 % шум, а docker держит 3 × 10 МБ — ошибки
вытеснялись за несколько дней. `setup_logging()` (вызывается в `main.py`): формат с именем
логгера; `httpx`/`httpcore`/`apscheduler.executors` — только WARNING; из access-лога uvicorn
отсеиваются **успешные** запросы к `QUIET_PATHS` (опрос табло, healthcheck) — 4xx/5xx на них
пишутся. Синк пишет **одну строку** с цифрами и длительностью. **`sync_log`** — журнал, который
переживает ротацию: `ok` только если данные записаны; сработавший предохранитель пустого
ответа — `skipped` (иначе `/api/sync/last` врал бы «синхронизировано только что»); падения
бэкафилла — `backfill/error` с днями. Сетевой сбой погоды — одна строка без трейса.
Сессия iikoweb проверяется (`/api/auth`) не чаще раза в `_SESSION_TRUST_SECONDS` (60 с), а не
перед каждым запросом: было 717 лишних запросов в час; протухшую сессию ловит 401/403.

### Порт кассы (`backend/pos/`) — граница с iiko/Saby
**Вся специфика кассы живёт только здесь.** `pos/base.py` — доменные типы (`PosOrder` с
`PosItem`/`PosPayment`, `PosProduct`, `PosDay`, `PosHour`, `PosOpenOrder`, плоская `ItemRow`)
+ протокол **`PosClient`** (`orders` / `products` / `revenue_days` / `hourly` / `open_orders` /
`history_start` / `warm`) + сборка строк БД из заказов (`to_item_rows`/`to_order_rows`/
`to_payment_rows`) и агрегаты для касс без отчётов (`aggregate_days`/`aggregate_hours`/
`aggregate_products`). Реализации: **`pos/iiko.py`** (разбор OLAP-строк `field0`, метрики
get-data, матрица часов — переехало из `scheduler`/`revenue.py`) и **`pos/saby.py`**
(сервисный токен, `retail/order/list` с пагинацией, каталог `retail/v2/nomenclature/list`
для категорий, агрегаты считаются у нас — у Saby агрегатов нет вообще). Адаптер Saby заранее
переживает белые пятна документации (пояс в `*WTZ`, страницы с 0 или с 1 — дедуп по `Sale`,
оплата без разбивки → «Прочее», «Статус» модификатором вне каталога — по имени строки 0 ₽,
категория по `id` или UUID) — таблица в `SABY_API.md`. TTL кэша табло — параметр
`open_orders(day, cache_ttl)` контракта, а не метод конкретного адаптера. Живой почасовой
агрегат (`aggregate_hours`) считает по часу ЗАКРЫТИЯ, как `hours_from_db`. Выбор — `get_pos()`
по `settings.pos_provider` (`POS_PROVIDER=iiko|saby`). Кассу дёргают только `scheduler`,
ручка табло `/api/orders/today`, живой fallback `order_store` и `_days_live`/`_hours` в
`revenue.py` — все через порт. Единственное исключение — диагностика `/api/dishes/order-types`
(сырое OLAP-поле iiko; при другом провайдере отдаёт пустой ответ с пояснением).
Покрытие iiko→Saby и белые пятна — в **`SABY_API.md`**.

### Синхронизация
`backend/scheduler.py` (APScheduler, таймзона `settings.timezone` = `Europe/Moscow`): `sync_revenue` и `sync_orders_recent` каждый час за 7 дней; **`sync_today` (выручка+заказы за 2 дня) каждые `settings.today_sync_seconds` (`TODAY_SYNC_SECONDS`, дефолт 180 c; 0 — выключить)** — держит «сегодня» свежим в БД, чтобы дашборд отдавал текущий день из БД, а не живым запросом (см. `_load_days` в `revenue.py`); ночью в 00:05 — `nightly` (`full_sync` + `backfill`). При старте (`lifespan` в `main.py`): `sync_revenue(31)` синхронно (выручка готова сразу), затем `run_startup_sync` (свежие заказы + `backfill`) — **в фоне через `asyncio.create_task`, чтобы выкачка истории не блокировала старт**. `RevenueDaily` обновляется по дню (upsert по PK-дате). **Заказы**: `sync_orders_range` берёт заказы у порта кассы (`get_pos().orders()`) и раскладывает их в `order_items`/`orders`/`order_payments` (replace по дням) хелперами `to_*_rows`; сама выборка — забота адаптера (у iiko это два OLAP-запроса: позиции [дата,час,заказ,категория,тип,имя]+[sum,qty,guests,cost,net] и заказ-атрибуты [время/касса/зал/стол/оплата] — оплата отдельно, чтобы сплит не дублировал позиции; у Saby — один `order/list` с пагинацией). `sync_dish_detail_day` — `dish_detail` по дню (`get_pos().products()`, нужен тип позиции). **`backfill`** заполняет всю историю один раз: `order_items` — одним запросом (быстро, сразу чинит OLAP-разрезы), `dish_detail` — по дню от **реального** начала истории (`min(order_items.date)`; probe по выручке может завысить старт) newest→oldest, пропуская заполненное; закрытые дни iiko неизменны → тянутся однократно. Начало истории — `settings.history_start_date` либо probe. **Предохранители истории** (`sync_window`): синк НЕ трогает дни раньше `settings.pos_switch_date` (`POS_SWITCH_DATE` — день, с которого работает текущая касса; иначе первый синк после переезда на Saby затёр бы историю iiko, которой больше нигде нет), а пустой ответ кассы поверх непустого дня в БД считается сбоем выборки и данные не затирает (`sync_orders_range`/`sync_dish_detail_day`). Каждый синк пишет в `SyncLog`; **ночью журнал чистится** — `prune_sync_log` удаляет записи старше `SYNC_LOG_KEEP_DAYS` (30; 0 — не чистить): при синке раз в 3 минуты это ~950 строк в день, и за три месяца `sync_log` разросся до 86 196 записей — больше, чем самих позиций заказов. **`POST /api/sync`** (`main.py`): без параметра — `full_sync` (выручка 31 дн + свежие заказы 7 дн, кнопка «Синхронизировать»); `?days=N` — лёгкий синк (`sync_revenue` + `sync_orders_recent` за N дней). Любой ручной синк **сбрасывает кэш** (`cache_clear()`). `GET /api/sync/last` — время последней успешной синхронизации.

### Кэш живых чтений
`backend/cache.py` — простой in-memory TTL-кэш (dict `key → (expiry, value)`). `get_metrics` и `olap_sales` в `iiko_web_client.py` кэшируют ответ по ключу из аргументов вызова (метрики/тип данных/даты/группировки) на `settings.cache_ttl_seconds` (`CACHE_TTL_SECONDS`, дефолт 60 c; 0 — выключить) через хелпер **`cached_or_call(key, factory)`**. Цель — схлопнуть повторные одинаковые живые запросы дашборда за один период. **Single-flight**: `cached_or_call` держит словарь `_inflight` future'ов по ключу — пока живой запрос в полёте, параллельные вызовы с тем же ключом ждут его результат, а не запускают свой (дашборд грузит несколько виджетов за период разом). Сбрасывается `cache_clear()` при ручном синке (`POST /api/sync`), чтобы кнопка «Синхронизировать» всегда давала свежие данные. **Протухшие ключи выметаются** (`_sweep` при разрастании словаря свыше `_SWEEP_AT`): `cache_get` удаляет только тот ключ, к которому обратились, а ключи содержат даты периода — то есть каждый новый период создавал новый ключ, и словарь рос вместе со значениями (ответы OLAP за месяц).

### БД
`backend/models.py` — SQLAlchemy, SQLite. Таблицы: `revenue_daily`, **`order_items`** (позиция заказа: дата/час/`order_num`/категория/имя/**`dish_type`** (DISH/MODIFIER/GOODS из OLAP)/qty/sum/**`net`** (после скидки)/**`cost`** (с/с iiko)/guests — источник ВСЕХ OLAP-разрезов из БД), **`dish_detail`** (per-day get-data: +`product_type`, источник таблицы блюд и фильтра модификаторов), **`orders`** (чек-сущность, **обогащённая**: дата/час/`weekday`/`daypart`/канал из «Статуса»/`is_delivery` (категория «Доставка»∨`_д`)/гости/`total_sum`/`cost_sum`/`item_count` (Σqty)/`dish_count`/**`pay_type`/`table_num`/`section`/`cashier`/`session_num`/`open_time`/`close_time`/`duration_min`** — последние из отдельного заказ-уровневого OLAP-запроса), **`order_payments`** (нормализация оплат: дата/`order_num`/`pay_type`/`amount` — один заказ ↔ несколько строк при сплит-оплате; OLAP делит сумму корректно, Σ=выручке). `orders`/`order_payments` — денормализованный снимок из заказов, **источник истины — `order_items`**; текущие эндпоинты их не читают, это задел под аналитику по чекам/оплатам. **Все эти таблицы — производные** (пересобираются бэкафиллом), при дрейфе схемы до-миграция в `init_db` дропает их по сентинел-колонке (`order_items`→`dish_type`, `orders`→`pay_type`) — данные не теряются. `dish_sales` (легаси, оконная — не используется), `sync_log` (продажи) + `suppliers`, `supplier_contacts` (телефоны/каналы: phone/whatsapp/telegram/email, много на поставщика), `supplier_files`, `ingredients`, `supplier_prices` (есть поле `brand` — торговая марка предложения), `ttk`, `ttk_ingredients`, `dish_mappings` (привязка POS-имя↔ТТК) (косты/ТТК) + `daypart_plan` (план: дневная норма выручки/ср.чека/гостей на дейпарт × группу дня недели). **Режим SQLite** (`models.py`, обработчик `connect`): **WAL** + `synchronous=NORMAL` +
`busy_timeout` (`SQLITE_BUSY_TIMEOUT_MS`, дефолт 5000). WAL нужен потому, что синк
заменяет данные по дням большими транзакциями ровно тогда, когда дашборд читает те же
таблицы; «database is locked» на проде не наблюдалось (0 в логах и `sync_log`), так что
это профилактика, а не лечение. Бэкап снимается через `sqlite3.Connection.backup()` — с
WAL совместим. **Тяжёлые чтения идут вне event loop**: `services/order_store.py` уносит
выборку и агрегацию в `asyncio.to_thread`, иначе месяц данных держал loop 716 мс, а в том
же процессе живёт ручка табло `/api/orders/today` (замер — `backend/tools/bench_loop.py`:
716 мс/9 пингов → 120–175 мс/~100 пингов).

`init_db()` создаёт схему (`create_all` идемпотентен — **новую таблицу добавляет без потери данных**); **миграций нет — при смене СУЩЕСТВУЮЩЕЙ схемы пересоздавать БД** (`docker compose down -v`; на проде перед этим — бэкап, см. `DEPLOY.md` «Бэкапы БД»: `down -v` стирает вбитые руками поставщиков/цены/ТТК, которых в iiko нет и бэкафилл их не вернёт). Файлы (накладные/прайсы) лежат в volume `/data/files` (`backend/storage.py`).

### Импорт ТТК/прайса
`backend/importers/ttk_matrix.py` парсит `backend/seed/ttk_matrix.xlsx` («ТТК и матрица продуктов», ~67 листов): «Матрица поставщиков» (прайс), «Матрица продуктов», «Сводная» (категории), лист-на-ТТК. **ТТК двухуровневые** (блюдо → п/ф → сырьё): строки резолвятся по нормализованному имени (`_norm` срезает «п/ф», ё→е, регистр), п/ф-ссылки предпочитают листы-полуфабрикаты. Канон-имя ТТК берётся из **имени листа** (B1 местами с копипаст-ошибкой). Разбор листа **независим от раскладки колонок** (`_col_map` ищет «с/с руб.»/«Выход» по шапке — у комбо они сдвинуты). **Порционная с/с (`cost_full`)**: строка «Итого с/с» листа (продукты+списания+упаковка) → «Сводная» → «Итого» рецепта (резерв для комбо); это надёжнее, чем неполная «Сводная». Идемпотентен (чистит ТТК/цены/ингредиенты, поставщиков апсёртит по `casefold`-ключу — SQLite `lower()` не трогает кириллицу!). **Канонизация + дедуп имён поставщиков**: алиасы (`_canon_supplier` + `SUPPLIER_ALIASES`, кросс-скрипт — WB/wildberries.ru → `wildberries.ru`; METRO/Мэтро/«METRO Chef …» → `METRO`; OZON/озон/ozon.ru → `Ozon`) + общий **ключ сопоставления `_supplier_key`** (lower, ё→е, срез `www.`/протокола/доменной зоны `.ru/.com`, только буквы/цифры — так «Turkish food»/«turkish-food»/«turkish-food.ru» = один). При импорте накопившиеся дубли **схлопываются**: контакты/файлы переносятся на «главного» (у кого их больше), имя приводится к канону, лишние строки удаляются. **Переживают реимпорт**: привязки `dish_mappings` (перелинковка по `name_norm` ТТК) и торговые марки `supplier_prices.brand` (снимок по поставщик+ингредиент). Запуск: `POST /api/import/ttk-matrix` или кнопка на странице Поставщики.

### API-слой
Коды метрик/типы данных/маппинги iiko вынесены в `backend/constants.py` (используй их, не хардкодь строки). **Переименование меню-категорий на дашборде** — `constants.CATEGORY_DISPLAY` + `utils.display_category()`: применяется единым выходным шагом во всех dishes-разрезах (`/api/dishes`, `check-composition`, `hourly-breakdown`, `basket`) и к подписям, и к ключам (чтобы drill/матч между виджетами не ломался; на детект доставки/модификаторов не влияет — те сверяют сырые имена). Сейчас: `«Меню» → «Допы и соусы»` (дефолтная корзина iiko с допами/соусами — Фри/Дип/Кетчуп/Перец). Роутеры в `backend/routers/`:
- `revenue.py` — `GET /api/revenue` (режим «Сумма»). **Источник дней — `days_stored_or_live`**: сводка `revenue_daily` → позиции `order_items` (`_days_from_items`, считает те же числа: выручка без служебных строк, чек = заказ) → и только за днями раньше начала истории либо за «сегодня», которого синк ещё не положил, идёт живая касса. Пробел внутри истории живым запросом НЕ добираем (день без заказов = закрытый день). Тем же путём берётся прошлый период для KPI-дельт. Раньше признаком был `is_custom` — любой выбор дат календарём уходил в кассу: `/api/pnl` за месяц стоил 8 403 мс против 373 мс из БД, и дашборд зависел от доступности кассы. **Почасовой разрез** (`_hours`) тоже из БД: `_hours_from_db` группирует `orders` по **часу ЗАКРЫТИЯ** (`close_time`) — именно так считает iiko, сверено на боевых данных (все 12 часов до рубля и до чека; по часу открытия расходилось на 1–2 %). В `summary.prev` — предыдущий сопоставимый период для **KPI-дельт** (`prev_period_range` в `utils.py`: **месяц/MTD сравнивается с тем же отрезком прошлого месяца**, день/неделя/диапазон — со скользящим окном той же длины; из БД, при отсутствии истории — живой запрос); в `prev_data` — выровненный по дню прошлый период для режима «Погода». К дням подмешивается погода (`weather.py`). `GET /api/revenue/hourly` — часы (`DATA_SUMMARY_BY_HOURS`). `GET /api/revenue/by-channel` и `/hourly-by-channel` — **выручка по дням/часам в разрезе каналов** (OLAP, хелпер `_channel_revenue`). `GET /api/revenue/by-weekday` — **свод по дням недели** (агрегат дней одного дня недели за период: кол-во дней, сумма/средняя выручка, чеки, ср. чек; источник тот же, что у `/api/revenue`). `GET /api/revenue/by-daypart` — **выручка/чеки/ср.чек по дейпартам** (Завтрак/Ланч/Полдник/Ужин/Ночь; границы в `DAYPARTS` (`constants.py`) из исторического «свода» ресторана): почасовые данные (`DATA_SUMMARY_BY_HOURS`) сворачиваются в окна, сумма сходится с `/api/revenue`. `GET /api/revenue/ops-report` — **ежедневный операционный отчёт** (аналог исторического Excel-свода «ОП»): дни периода (столбцы) × дейпарты (строки), по каждой клетке — выручка/чеки/гости/средний чек/**food cost %**. Источник — **один OLAP-запрос** по `[дата, час, OrderNum, категория, имя]` + `DishSumInt`/`DishAmountInt`/**`GuestNum`** (гости — атрибут заказа, берём раз на `OrderNum`); часы свёрнуты в окна `DAYPARTS`. Food cost = с/с порций (`_dish_unit_cost` из `dishes.py`, ТТК `cost_full`) ÷ выручка **блюд с привязкой** (+ поле `coverage` — какая доля выручки окна покрыта ТТК). Справа — `total` (Факт за период), `avg_per_day` (Среднее на активный день), `revenue_share` (доля дейпарта). Плюс **food cost % по группам категорий** (`category_groups`/`category_totals` + `categories` на дейпарт): группа категории через `_category_group` (`DRINK_CATEGORIES`→Напитки, `ALCOHOL_CATEGORIES`→Алкоголь — пуст у точки, остальное→Еда) — нижний блок свода. **Слой плана**: к каждому дейпарту и итогу подмешиваются `plan`/`plan_pct` (Факт/План/% к плану) из таблицы `daypart_plan` (роутер `plan.py`) — план задаётся **дневной нормой на (дейпарт × группа дня недели** `WEEKDAY_GROUPS`/`WEEKDAY_TO_GROUP`), на период масштабируется умножением на число подходящих дней (`_period_plan`, `group_day_count`) — поэтому `% к плану` честен для день/неделя/MTD/диапазона. `has_plan` — задан ли план. Скидок у точки нет (метрика = 0), поэтому `DishSumInt` численно совпадает с `REV_GROSS`. **Роутер `plan.py`** (`prefix=/api/plan`): `GET` — матрица норм, `PUT` — сохранить, `POST /seed-from-history?months=N` — автозаполнить средними дневными нормами из истории (OLAP). `GET /api/revenue/kpi-by-channel` — KPI в разрезе **доставка / не доставка** (брутто-суммы по каналам). `GET /api/revenue/by-payment` — **структура выручки по способам оплаты** (Карта/Наличные/Агрегатор): доли по выручке и чекам за период (`totals`) + дневной стек-тренд (`daily`). Источник — таблица `order_payments` (сплит-чек разложен на строки, Σ=выручке до рубля); группировка `pay_type` → группа через `utils.payment_group()` (`PAYMENT_GROUP_RULES`/`PAYMENT_GROUP_ORDER` в `constants.py`, матч по подстроке). Только из БД (для дат старше начала истории оплат — пусто). При `include_delivery=false` исключаются оплаты доставочных заказов (`orders.is_delivery`) — агрегатор (Яндекс Еда = доставка) тогда исчезает. **Параметр `include_delivery` (по умолчанию `true`)** для галки «без доставки»:
- В `revenue.py` (`/api/revenue`, `/api/revenue/hourly`, `/api/revenue/by-weekday`, `/api/revenue/by-daypart`): при `false` бэкенд вычитает выручку и чеки доставки (OLAP, хелперы `_delivery_buckets`/`_exclude_delivery`; доставка = меню-категория «Доставка», чек = заказ с такой позицией) из REV_GROSS-дней/часов — и из текущего, и из прошлого периода (чтобы KPI-дельты сравнивали сопоставимое). С/с по каналам не делится, поэтому `food_cost_pct`/`cost_sum` остаются по всей точке (в `by-weekday` food cost считается от полной выручки дня).
- **Что считается доставкой для галки** (`include_delivery=false`): **меню-категория «Доставка» ИЛИ имя позиции с маркером `_д`** (напр. «Дюрюм_д»). Единое правило — хелпер **`utils.is_delivery(category, name)`** (категория точным совпадением, `_д` — токеном в любом месте имени, регистронезависимо); используется во всех revenue/dishes-разрезах. Отсев **по-позиционно**, БЕЗ правила модификатора «Статус» и БЕЗ распространения на весь заказ. **`ChecksDistribution` теперь тоже управляется галкой** (`check-distribution`/`by-channel` принимают `include_delivery`): при выкл доставочные заказы/канал исключаются, плюс фронт **дополнительно скрывает строку «Доставка»** из разреза (фильтр в `ChecksDistribution.tsx`). В виджете **нет эмодзи** — метрики подписаны текстом «Чеки»/«Выручка». 3-way разрез на дашборде `Delivery` (`kpi-by-channel`/`service-breakdown`) по-прежнему опирается на «Статус» заказа и галкой не управляется.
- В `dishes.py` (`/api/dishes`, `/hourly-breakdown`, `/check-composition`, `/check-fullness`): при `false` отсекаются позиции категории «Доставка». `/api/dishes` просто фильтрует строки get-data (там уже есть категория) — без OLAP. OLAP-разрезы пропускают строки с `DishCategory == «Доставка»` (в `hourly-breakdown?group=dish` категория для этого добавляется в группировку). Заказ, целиком доставочный, после отсева исчезает сам (не остаётся товарных позиций).
- `dishes.py` — `GET /api/dishes` живой запрос за период; `group_by=dish|category`; **исключает `productType=MODIFIER`**; с/с per-portion = `Ttk.cost_full` × кол-во, **только не-п/ф** (коллизия имён п/ф↔блюдо); источник по блюду — ручная `DishMapping`, иначе авто-совпадение имени; поле `channel` = «доставка», если `is_delivery` (категория «Доставка» или имя с `_д`). **Флаг `has_cost`**: без ТТК-привязки `cost_sum=0`, а `cost_pct/margin_pct=null` (не выдаём мнимую 100% маржу; на фронте — «—»); для категории `has_cost` истинно, только если у **всех** её блюд есть привязка. `check-distribution` — чеки по типу обслуживания (**уникальные заказы** по каналу через OLAP `OrderNum`+«Статус»; сумма по типам = числу чеков, не кол-ву модификаторов). `hourly-breakdown?group=category|dish` — продажи по часам (блюда/категории, OLAP; в режиме `dish` каждый item несёт `category` — для drill-down «категория→блюда» на фронте). `basket` — **матрица сочетаемости** (market basket, #14): что чаще берут вместе в одном чеке (`group=category|dish`); возвращает `labels`/`matrix` (со-встречаемость пар в чеках) + `pairs` (топ-пары с `support`/`confidence`); OLAP по `OrderNum`. `service-breakdown` — блюдо×канал (OLAP по `OrderNum`+«Статус»). `check-composition` — средняя доля категорий в чеке (по кол-ву/выручке, период/часы). `check-fullness` — распределение чеков по числу позиций (1/2/3/4+) по часам, где **позиция = единица товара** (сумма `qty` по заказу, дробный вес округляется), а не число разных блюд. **Исключение модификаторов из OLAP-разрезов**: OLAP не отдаёт `productType`, поэтому хелпер `_modifier_filters` берёт имена+категории `productType=MODIFIER` из `dishes_detail` и отсекает их в `hourly-breakdown`/`service-breakdown`/`check-composition`/`check-fullness`/`basket` (модификаторы вроде «Разрезать 1/2» — не блюда). **Категорию отсекаем по `cats`, ТОЛЬКО если она ЦЕЛИКОМ модификаторная** (нет ни одного `DISH` — «модификаторы»/«Статус»): `cats = cat_has_mod − cat_has_dish`. **Смешанные категории НЕ отсекаются** (`Напитки`, `Доставка` содержат и блюда, и модификаторы-добавки) — иначе из всех OLAP-разрезов пропадала вся категория (баг: «Напитки» — 3-я по выручке — исчезала из состава чека, наполненности и т.д.). Отдельные модификаторы-строки в смешанной категории по имени не вычистить: платные «Кола»/«Айран» в OLAP **слиты** с одноимёнными блюдами (один `(name, category)`), отсев по имени убил бы реальные продажи; остаётся лишь бесплатный «Айран_» (rev=0) — пренебрежимо. «Статус» при этом сначала даёт канал, потом отсекается. `order-types` — диагностика поля OrderType (пуст у точки).
- `suppliers.py` — CRUD; **`DELETE /{id}`** — удаление поставщика (каскад контактов/цен/файлов + физические файлы через `storage.delete_file`; кнопка-корзина в списке Поставщики); `/{id}/contacts` (POST/PUT/DELETE, валидация `normalize_phone`/`normalize_email`); `/{id}/products/{price_id}` PUT — торговая марка; `/export` → xlsx (openpyxl); файлы (`UploadFile`/`FileResponse`).
- `nomenclature.py` — `prefix="/api"`, `/ingredients` (GET список/карточка + `PUT /{id}` правка), `/ttk` (каталог + карточки), `/dish-mappings` (GET/POST/DELETE).
- `imports.py` — запуск импорта.
Все роутеры с периодом принимают `period` **или** `date_from/date_to` (диапазон приоритетнее). `period_range` (`utils.py`): `day` = сегодня, **`week` = с понедельника текущей недели по сегодня** (не последние 7 дней; `prev_period_range` для недели сдвигает на 7 дней назад), **`month` = с 1-го числа текущего месяца по сегодня (MTD)**, не последние 30 дней. **«Сегодня» считается в часовом поясе ресторана** (`utils.today()` → `settings.timezone`, не TZ контейнера). `full_sync` синкает 31 день, чтобы MTD всегда был в БД. Производные метрики (food cost %, маржа, доли, дельты, с/с %) считаются **на лету в питоне**. Хелперы каналов/нормализации — в `utils.py`. `weather.py` — погода Москвы из Open-Meteo (кэш в памяти, не критична; **только дневная температура `temp_max`** — ночную `temp_min` не тянем и не показываем). **Свежие даты (последние 7 дней + сегодня) тянутся из forecast-API, более старые — из archive-API** (archive отстаёт на ~5 дней и отдаёт свежие дни с 400 → раньше weather=None для свежих дат); граница — `today() − 7`.

**Доступ к заказам из БД** (`backend/services/order_store.py`) — **источник всех разрезов**: `order_rows(group_fields, data_fields, date_from, date_to)` повторяет контракт `olap_sales` (те же строки `field0`/`field1..`), агрегируя `order_items` из БД (SUM для sum/qty, MAX для guests; склейка group-значений через «, »); `dish_detail_rows(date_from, date_to)` повторяет `dishes_detail`. Поэтому **роутеры и весь даунстрим-разбор (`split_field_*`) не изменились** — переключены лишь вызовы `iiko_web.olap_sales`/`dishes_detail` → `order_rows`/`dish_detail_rows` (в `dishes.py`/`revenue.py`/`plan.py`/`services/delivery.py`). Для периодов внутри сохранённого окна — из БД; для диапазонов старше начала истории — **живой fallback** к кассе через порт (`get_pos().orders()` → `to_item_rows` → та же агрегация). Формат `field0` остался внутренним контрактом разрезов и от кассы не зависит. Парити с живым API проверена (0 расхождений). Исключение — диагностика `/api/dishes/order-types` (живой `olap_sales`, OrderType в БД не храним; только при `POS_PROVIDER=iiko`). ⚠️ **История продаж iiko живёт только в нашей БД** — Saby знает лишь свои продажи, поэтому до отключения iiko бэкафилл обязан быть полным, а БД — забэкаплена.

**Ключ заказа — пара (дата, номер), а не номер.** Номер заказа уникален только внутри дня (в iiko нумерация начинается заново каждое утро). Поэтому все разрезы «по чекам» обязаны держать дату в группировке: поля даёт **`services/olap_parse.order_group_fields(bucket)`**, разбирает строку **`split_order_row(value, bucket)`** → `(ключ «дата|номер», корзина, категория, имя)`. Так работают `check-distribution`, `check-fullness`, `check-composition`, `basket`, `service-breakdown`, `kpi-by-channel`, `by-channel`, `hourly-by-channel` и `delivery_buckets`. ⚠️ Группировка по одному `OrderNum` склеивает заказы разных дней в один: до фикса (25.09.2026) за 01–20.09 из 3 310 чеков получалось 237 «чеков» по 39,7 позиции вместо 2,5 — врали наполненность, состав чека, сочетаемость и доли каналов. Регрессия закрыта тестами `tests/test_order_key.py`. Если у заказа несколько «Статусов» (кассир отметил и «Доставка», и «С собой»), канал выбирается детерминированно — `utils.stronger_channel` по `CHANNEL_PRIORITY` (доставка > с собой > в зале), а не по порядку строк в ответе.

**OLAP-движок** (`iiko_web_client.olap_sales`) — теперь используется планировщиком (синк/бэкафилл) и fallback'ом. Для разрезов, которые `get-data` не умеет (блюдо×час, блюдо×канал, состав/наполненность чека). Поток: `POST /api/olap/init` → поллинг `fetch-status/{hash}` → `fetch/{hash}/simple` → `result.rows` (`field0` = склейка group-полей через «, », далее data-поля). **Тип обслуживания у точки НЕ в `OrderType` (пуст)** — берётся из модификатора категории «Статус» на уровне заказа: группировка по `OrderNum` связывает блюда заказа с его «Статусом». Поля/тип/вью и нетоварные категории — в `constants.py` (`OLAP_*`, `ORDER_STATUS_*`, `DELIVERY_CATEGORY`, `NON_PRODUCT_CATEGORIES`). Подробности полей — в `IIKO_WEB_API.md`. **dateTo в фильтре `date_range` по `OpenDate.Typed` — ВКЛЮЧИТЕЛЬНЫЙ целый день** (живой API игнорирует `includeRight=False`): передавать `dateTo = date_to` как есть, **без +1** — иначе в выборку попадёт лишний день после диапазона (для одного дня это удваивало все OLAP-метрики).

### Фронт
React 19 + Vite + TS, **react-router** (роуты в `App.tsx`, layout с `Sidebar`). Страницы в `src/pages/`: `Dashboard`, `Delivery` (отдельный дашборд доставки — пункт сайдбара `/delivery`), `Suppliers`, `SupplierCard`, `NewSupplier`, `Nomenclature`, `TtkCard`. **Дашборд разбит на 3 вкладки** (стейт `tab` в `Dashboard.tsx`, KPI-карточки всегда сверху): **Пульс** (RevenueChart + ChecksDistribution + PaymentStructure; **при одном дне** — `isSingleDay` в `Dashboard.tsx` — вместо вырожденного «по дням» показывается `HourlyChart` с внутридневной динамикой), **Операции** (плоский порядок): WeekdaySummary → OpsReport → HourlyChart → CheckFullness → HourlyBreakdown → DaypartBreakdown; OpsReport и WeekdaySummary скрыты при одном дне, **HourlyChart при одном дне скрыт на «Операциях»** (он уже показан на «Пульсе» вместо вырожденного «по дням» — без дубля), **Меню** (порядок): DishTable → MenuBasket → MenuEngineering → CheckComposition. **Глубокий анализ каналов** (доставка / зал / с собой) живёт на отдельном дашборде `Delivery`; в Пульсе оставлена карточка `ChecksDistribution` — наглядный разрез чеков/выручки по типу обслуживания (**реагирует на галку «С доставкой»**: при выкл доставка исключается). Сверху — **галка «С доставкой»** (`withDelivery` в `Dashboard.tsx`, по умолчанию **выкл**, **без эмодзи**): выкл → **все виджеты дашборда** получают данные с `include_delivery=false` и показывают цифры **без доставки**. Рядом — кнопка «Синхронизировать» (полный синк) с подписью времени последней синхронизации (`fmtSync`: **сперва время, затем дата** — «14:05 · 23.06», МСК) и **селектор автосинхронизации** (`autoSyncMs`, опции `AUTOSYNC_OPTIONS` в `constants.ts`: выкл / 5 / 15 / 30 мин / 1 час; хранится в localStorage). При выбранном интервале `useEffect` ставит `setInterval`, который раз в интервал делает лёгкий синк (`triggerSync(AUTOSYNC_DAYS=7)`) + рефетч. Затрагивает revenue-виджеты (KpiCards, RevenueChart, HourlyChart, WeekdaySummary, DaypartBreakdown, OpsReport) и меню/блюда-виджеты (CheckFullness, HourlyBreakdown, CheckComposition, MenuEngineering, DishTable). Компоненты дашборда (что показывает каждый — в `README.md`): `KpiCards` (Выручка/Средний чек/Чеков с дельтами к пр. периоду; **все три из одного источника `REV_GROSS`** `/api/revenue` — сходятся между собой; разбивка по каналам убрана отсюда и вынесена на отдельный дашборд `Delivery`, чтобы не смешивать `REV_GROSS` и OLAP), `RevenueChart` («Выручка по дням»: режимы Сумма/По статусам (стек по каналам, `/api/revenue/by-channel`; **реагирует на галку «С доставкой»** — при выкл запрос идёт с `include_delivery=false` и канал «доставка» убирается из стека)/Погода, **форма всегда столбчатая** — переключатель типа графика убран как косметика (дни — дискретные корзины; линия/область рисовали бы ложную непрерывность и не несут раскраску по дням недели); фильтр дней — **скрыт при одном дне**; подпись дня на оси X — «Пн 22.06» (день недели + число в формате DD.MM, хелпер `dayLabel`/`dm`), под ней погода **структурно** (иконка · температура · дельта `(±°)` к тому же дню прошлого периода, цвет дельты: теплее `warn` / холоднее `accent`); в «Сумма» — один ряд выручки, **столбцы окрашены по группе дня недели** (`WEEKDAY_GROUPS` в `constants.ts`: Пн / Вт-Ср / Чт / выходные Пт-Вс) с легендой групп; **ср. чек и чеки не отдельными столбцами, а в кастомной подсказке** `SumTooltip`; опорная линия среднесуточной выручки), `WeekdaySummary` («Свод по дням недели»: строки окрашены по группе дня недели `WEEKDAY_GROUPS`, **фикс-порядок Пн→Вс** (сортировка/инлайн-бары убраны)), `DaypartBreakdown` («Выручка по дейпартам»: столбцы выручки по окнам дня Завтрак/Ланч/Полдник/Ужин/Ночь + доля над столбцом + таблица выручка/доля/чеки/ср.чек; **Раскладка:** `#root` без `max-width` — дашборд во всю ширину экрана.
