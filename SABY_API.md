## Авторизация

`POST https://online.sbis.ru/oauth/service/`

```json
{"app_client_id": "…", "app_secret": "…", "secret_key": "…"}
```

Ответ (живьём): `{"access_token": "…", "sid": "…", "token": "…"}`. Дальше в каждом
запросе заголовок **`X-SBISAccessToken: <token>`**. Выход — POST с параметром `token`.

**TTL токена не документирован.** Держим не дольше `SABY_TOKEN_TTL_SECONDS` (1 час) и
перезапрашиваем при 401/403 с одним повтором — та же схема, что у cookie-сессии iiko.

## Продажи — главный (и единственный) источник данных

`GET https://api.sbis.ru/retail/order/list`

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `pointId` | integer | да | идентификатор точки продаж |
| `fromDateTime` | `YYYY-MM-DD hh:mm:ss` | да | начало выборки |
| `toDateTime` | `YYYY-MM-DD hh:mm:ss` | нет | конец выборки |
| `page` | integer | нет | номер страницы |
| `pageSize` | integer | нет | записей на страницу, **макс. 100**, по умолчанию 30 |
| `needDiscountInfo` | boolean | нет | добавить сведения о скидках |

Ответ: `{"orders": [...], "outcome": {"hasMore": true|false}}`. **На пустой выборке
`orders` приходит как `{}`, а не `[]`** (проверено живьём) — код это нормализует.

### Продажа (чек)

| Поле | Тип | Что это | Нужно нам |
|---|---|---|---|
| `Number` | **string** | номер продажи | да — номер заказа для табло |
| `Sale` / `Key` | integer / string | id и ключ продажи | резерв |
| `DateWTZ` | datetime | дата продажи | да |
| `OpenedWTZ` / `ClosedWTZ` | datetime | открытие / закрытие чека | да — час, длительность |
| `Updated` | datetime | дата изменения продажи | резерв (инкрементальный синк) |
| `Deleted` | boolean | продажа удалена | да — отбрасываем |
| `Return` / `ReturnSale` | boolean / integer | возврат и по какой продаже | да — считаем возвраты |
| `ShiftNumber` / `Shift` | string / integer | номер и id кассовой смены | да |
| `Teller` | integer | **id** кассира (имени нет) | да, как id |
| `TotalPrice` / `TotalDiscount` | number | сумма и скидка продажи | да |
| `Customer` / `CustomerName` | integer / string | клиент | нет |
| `Warehouse` / `Company` / `Seller*` | — | склад, компания, продавец | нет |
| `DiscountInfo[]` | array | `Name`, `PercentValue`, `Value` | при скидках |

### Позиция продажи (`SaleNomenclatures[]`)

| Поле | Тип | Что это | Нужно нам |
|---|---|---|---|
| `Name` / `ShortName` | string | имя позиции | да |
| `Nomenclature` | integer | id номенклатуры | да — по нему берём категорию из каталога |
| `NomenclatureUUID` / `NomenclatureNumber` | string | ключ и код товара | резерв |
| `Quantity` | number | количество | да |
| `TotalPrice` | number | сумма по позиции | да (нетто) |
| `TotalDiscount` | number | скидка по позиции | да (брутто = сумма + скидка) |
| `CheckPrice` / `CheckSum` | number | цена и сумма в чеке | резерв |
| **`PlannedCost`** | number | **плановая себестоимость** (по ТТК кассы) | да — food cost |
| **`TotalCost`** | number | **фактическая себестоимость** (по складу) | да — резерв к плановой |
| **`IsModifier`** | boolean | **позиция — модификатор** | да — фильтр «только блюда» |
| `IsKit` / `KitSettings` | boolean | комплект | резерв (комбо) |
| `Positions[]` | array | **дочерние позиции** (модификаторы, состав) | да — разбираем рекурсивно |
| `IsReturn` / `Refused` / `ReasonName` | boolean / string | возврат, отказ и причина | да — резерв |
| `TotalVAT` / `Unit*` / `Package` / `Barcode` | — | НДС, упаковка, штрихкод | нет |

### Оплаты (`Payments[]`)

| Поле | Тип | Что это |
|---|---|---|
| `Amount` | number | сумма платежа |
| `CashSum` / `PayCash` | number | наличными |
| `BankSum` / `PayBank` | number | безналичными |
| **`BankType`** | string | тип безнала (напр. «Сбербанк») |
| `CertificateSum` / `PaySalary` | number | сертификат / под зарплату |
| `CheckNumber`, `KKM`, `KKMName`, `KKTNumber` | — | чек и касса |
| `FiscalNumber`, `FiscalSign`, `Nonfiscal` | — | фискальные признаки |
| `OpenedWTZ` / `ClosedWTZ` / `CarriedWTZ` | datetime | открытие, закрытие, пробитие чека |

Сплит-оплата видна нативно: несколько сумм в одном платеже и/или несколько платежей.

## Каталог номенклатуры (категории блюд)

`GET https://api.sbis.ru/retail/v2/nomenclature/list` — `pointId`, `priceListId`,
`pageSize` (макс. 1000), `page`, `folder`, `searchString`, `withBalance`, `withBarcode`,
курсорная навигация (`position` + `order`).

Поля: `id`, `name`, `cost`, `unit`, `description`, `images[]`, `article`, `nomNumber`,
`externalId`, `isKit`, `published`, `attributes`, `balance`, `modifiers[]` (`id`, `name`,
`cost`, `minCount`, `maxCount`, …), `barcodes[]`, и **иерархия**: `hierarchicalId`,
`hierarchicalParent`, `isParent`. **Вложенность до 3 уровней** («Папка/Папка/Позиция»).

Отсюда мы берём **категорию** (имя папки-родителя) и **тип позиции** (по корневой папке:
«Блюда» → DISH, «Товары/Продукты/Полуфабрикаты» → GOODS). В самой продаже категории нет.

## Точки продаж

`GET https://api.sbis.ru/retail/point/list` — `pointId`, `product` (`delivery`/`retail`),
`withPhones`, `withPrices`, `withSchedule`, `page`, `pageSize` (0–500).
Ответ: `salesPoints[]` с `id`, `name`, `address`, `locality`, `latitude`/`longitude`,
`defaultPriceList`, `prices[]`, `phones[]`, `worktime`/`schedule`, а живьём ещё
`halls[]`, `paymentKinds[]`, `deliverySettings`, `product[]`.

## Вебхуки (замена поллинга)

Настройка руками в кабинете: **Настройки → Кастомизация → Триггеры → «+» → Бизнес /
Розница и кассы / Продажи розницы → «Изменения информации о продажах»**, действие
«Отправить HTTP-запрос», в блоке URL — адрес нашей ручки. **Тело, заголовки и авторизация
задаются нами в самом триггере** — то есть формат вебхука мы определяем сами, а не
подстраиваемся под чужой. Документация не описывает ни гарантий доставки, ни повторов,
ни подтверждения получения.

## Чего в Saby API НЕТ (проверено по документации всех разделов)

1. **Агрегатов и отчётов.** Нет аналога `POST /api/kpi/dashboard/get-data` (метрики
   выручки/чеков/среднего чека) и нет OLAP-движка. Есть только выгрузка продаж.
   Разделы «Отчетность» и ОФД — про налоги и фискальные чеки, не про аналитику.
2. **Типа обслуживания** в продаже (зал / с собой / доставка).
3. **Числа гостей**, **номера стола**, **зала** в продаже (зал есть в карточке точки,
   но `halls` у нас пуст).
4. **Имени кассира** — только `Teller` (id).
5. **Категории номенклатуры** в позиции продажи — только id, категория из каталога.
6. Фильтра по `Updated` в `order/list` — инкрементальный синк «по изменённым» не выйдет,
   только по датам продаж.

## Покрытие: что было в iiko и что будет в Saby

Таблица по каждому источнику данных, который сегодня использует дашборд и табло.

| Что нужно | iiko сегодня | Saby | Итог |
|---|---|---|---|
| Заказы: номер, время открытия/закрытия | OLAP `OrderNum`/`OpenTime`/`CloseTime` | `Number`, `OpenedWTZ`, `ClosedWTZ` | ✅ равноценно |
| Позиции чека: имя, кол-во, сумма | OLAP `DishName`/`DishAmountInt`/`DishSumInt` | `SaleNomenclatures[]` | ✅ равноценно |
| Категория блюда | в ответе `get-data` (`decoration.product`) | отдельный запрос каталога + join по id | ⚠️ работает, но **зависит от того, как заведены папки меню** |
| Тип позиции (блюдо/товар/модификатор) | `productType` из `get-data` | `IsModifier` + корневая папка каталога | ✅ **лучше**: флаг модификатора приходит в самой продаже |
| Себестоимость позиции | `ProductCostBase` (в iiko не заполнена → food cost сломан) | `PlannedCost` (ТТК) + `TotalCost` (склад) | ✅ **лучше**, если завести ТТК в Saby |
| Скидки | метрика = 0 (скидок нет) | `TotalDiscount` + `DiscountInfo[]` | ✅ равноценно |
| Оплаты (нал/карта/сплит) | OLAP `PayTypes`, сплит строками | `Payments[]` с `CashSum`/`BankSum`/`BankType` | ✅ **лучше**: структура нативная |
| Кассовая смена | OLAP `SessionNum` | `ShiftNumber` | ✅ равноценно |
| Кассир | OLAP `Cashier` (имя) | `Teller` (**только id**) | ⚠️ имя теряется |
| Выручка/чеки/ср. чек по дням | метрики `REV_GROSS`/`TRN_ALL`/`AVERAGE_SPEND_GROSS` | считаем сами из заказов | ✅ равноценно (уже считаем из БД) |
| Выручка по часам | `DATA_SUMMARY_BY_HOURS` | считаем сами из заказов | ✅ равноценно |
| Дейпарты, свод по дням недели, ОП-отчёт, план | производные от часов/заказов | то же | ✅ равноценно |
| Меню-инжиниринг, ABC, состав чека, сочетаемость | OLAP по заказам | то же из заказов | ✅ равноценно |
| **Канал: зал / с собой / доставка** | модификатор категории «Статус» в заказе | **нет поля**; остаётся правило по позиции (категория «Доставка» ИЛИ имя с `_д`) | ❌ **дырка**: 3-way разрез (`Delivery`-дашборд, `ChecksDistribution`) без «Статуса» схлопнется в «доставка / не доставка» |
| **Гости, ср. чек на гостя** | OLAP `GuestNum` | **нет** | ❌ пропадает (в ОП-отчёте строка «Гости» станет нулевой) |
| Стол, зал | OLAP `TableNum`/`RestaurantSection` (у фастфуда и так пусты) | нет (залы не настроены) | ⚠️ де-факто не теряем |
| Возвраты | метрика `REFUND_TRN` | `Return` у продажи | ✅ равноценно |
| **История продаж до переезда** | вся история в iiko | Saby знает только свои продажи | ❌ **iiko-историю надо выкачать в нашу БД ДО отключения iiko** |
| Табло: заказы за сегодня | живой OLAP, ответ за секунды | `order/list` за сегодня (или вебхук) | ✅ равноценно, вебхук даже быстрее |

Итог одной строкой: **по продажам и деньгам Saby покрывает iiko полностью и местами
лучше** (себестоимость, оплаты, модификаторы); **теряются три вещи** — тип обслуживания
заказа, число гостей и имя кассира; **и история продаж iiko не переносится сама**.

## Что проверить на первом живом чеке

Пока в Saby ноль продаж, эти пункты закрыть нечем — они зафиксированы как ожидания в
`backend/tests/test_pos_saby.py` (фикстура собрана по документации, не с кассы):

1. Приходят ли в продаже **недокументированные поля**: тип обслуживания, гости, стол,
   зал — Presto ресторанный, поля могли просто не попасть в документацию.
2. `TotalPrice` позиции — это сумма **до** или **после** скидки (мы считаем «после»,
   а брутто = `TotalPrice + TotalDiscount`).
3. Заполняется ли `PlannedCost` без заведённых ТТК (ожидаем 0) и `TotalCost` без
   складских документов.
4. Как выглядит **номер продажи**: сквозной за смену, с префиксом, буквами?
   От этого зависит миграция схемы табло (`orders.number INTEGER` → текст).
5. Как в позициях выглядят **модификаторы**: отдельной строкой верхнего уровня или в
   `Positions[]` внутри блюда (мы разбираем оба случая).
6. Есть ли пагинация при большом дне (>100 чеков) и правда ли `hasMore` работает.
7. Что в `Payments[].BankType` для оплаты через агрегатор (Яндекс Еда), если она будет.

## Действия в кабинете Saby (нужны от владельца)

1. **Завести меню** (сейчас позиций 0): структура папок внутри «Блюда» = наши
   меню-категории (Дюрюмы, Напитки, Комбо, Допы и соусы…). Вложенность до 3 уровней.
   Категории дашборда берутся именно оттуда — как назовём папки, так и будет в отчётах.
2. **Поправить режим работы точки**: 12:00–22:00 **ежедневно** (сейчас сб/вс выходные).
3. **Решить, как помечать канал** (зал / с собой / доставка): либо залы в Presto, либо
   отдельные позиции меню с маркером `_д`, как сейчас в iiko. Без решения 3-way разрез
   каналов не переедет.
4. **Решить про гостей**: если разрез по гостям нужен, требуется поле в Presto (или
   отказаться от строки «Гости» в ОП-отчёте).
5. **Завести ТТК в Saby** — тогда `PlannedCost` даст настоящий food cost по кассе
   (сейчас он сломан: в iiko себестоимость не заполнена).
6. **Пробить один тестовый чек** (хоть на 10 ₽, лучше два: обычный и со сплит-оплатой) —
   это единственный способ закрыть список выше.
