## Авторизация

`POST https://online.sbis.ru/oauth/service/`

```json
{"app_client_id": "…", "app_secret": "…", "secret_key": "…"}
```

Ответ (живьём): `{"access_token": "…", "sid": "…", "token": "…"}`. Дальше в каждом
запросе заголовок **`X-SBISAccessToken: <token>`**. Выход — POST с параметром `token`.

**TTL токена не документирован.** Держим не дольше `SABY_TOKEN_TTL_SECONDS` (1 час) и
перезапрашиваем при 401/403 с одним повтором — та же схема, что у cookie-сессии iiko.

## Продажи — главный (и единственный) источник данных

`GET https://api.sbis.ru/retail/order/list`

| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `pointId` | integer | да | идентификатор точки продаж |
| `fromDateTime` | `YYYY-MM-DD hh:mm:ss` | да | начало выборки |
| `toDateTime` | `YYYY-MM-DD hh:mm:ss` | нет | конец выборки |
| `page` | integer | нет | номер страницы |
| `pageSize` | integer | нет | записей на страницу, **макс. 100**, по умолчанию 30 |
| `needDiscountInfo` | boolean | нет | добавить сведения о скидках |

Ответ: `{"orders": [...], "outcome": {"hasMore": true|false}}`. **На пустой выборке
`orders` приходит как `{}`, а не `[]`** (проверено живьём) — код это нормализует.

## Каталог номенклатуры (категории блюд)

`GET https://api.sbis.ru/retail/v2/nomenclature/list` — `pointId`, `priceListId`,
`pageSize` (макс. 1000), `page`, `folder`, `searchString`, `withBalance`, `withBarcode`,
курсорная навигация (`position` + `order`).

Поля: `id`, `name`, `cost`, `unit`, `description`, `images[]`, `article`, `nomNumber`,
`externalId`, `isKit`, `published`, `attributes`, `balance`, `modifiers[]` (`id`, `name`,
`cost`, `minCount`, `maxCount`, …), `barcodes[]`, и **иерархия**: `hierarchicalId`,
`hierarchicalParent`, `isParent`. **Вложенность до 3 уровней** («Папка/Папка/Позиция»).

Отсюда мы берём **категорию** (имя папки-родителя) и **тип позиции** (по корневой папке:
«Блюда» → DISH, «Товары/Продукты/Полуфабрикаты» → GOODS). В самой продаже категории нет.

## Точки продаж

`GET https://api.sbis.ru/retail/point/list` — `pointId`, `product` (`delivery`/`retail`),
`withPhones`, `withPrices`, `withSchedule`, `page`, `pageSize` (0–500).
Ответ: `salesPoints[]` с `id`, `name`, `address`, `locality`, `latitude`/`longitude`,
`defaultPriceList`, `prices[]`, `phones[]`, `worktime`/`schedule`, а живьём ещё
`halls[]`, `paymentKinds[]`, `deliverySettings`, `product[]`.

## Вебхуки (замена поллинга)

Настройка руками в кабинете: **Настройки → Кастомизация → Триггеры → «+» → Бизнес /
Розница и кассы / Продажи розницы → «Изменения информации о продажах»**, действие
«Отправить HTTP-запрос», в блоке URL — адрес нашей ручки. **Тело, заголовки и авторизация
задаются нами в самом триггере** — то есть формат вебхука мы определяем сами, а не
подстраиваемся под чужой. Документация не описывает ни гарантий доставки, ни повторов,
ни подтверждения получения.

## Правила работы с API (проверено живьём 25.09.2026)

Список поведений, которые документация не описывает, а знать их обязательно.

| Правило | Как проверено | Что делаем |
|---|---|---|
| **Неизвестный `pointId` → HTTP 200 и пустая выборка**, а не ошибка | запрос с `pointId=999999` | `SabyPos._ensure_point()` сверяет точку через `point/list` и падает с понятным текстом: иначе опечатка в настройке выглядела бы как «продаж нет» |
| Пустая выборка приходит как `{}`, а не `[]` (и `orders`, и `nomenclatures`, и `priceLists`) | пустые периоды | `_as_list()` нормализует любой из видов |
| Битый токен → **HTTP 401 с HTML-страницей логина**, не JSON | запрос с мусорным токеном | 401/403 ловим до разбора тела: сбрасываем токен и повторяем один раз |
| Токен живёт **дольше часа** (проверен через 1,5 ч) | повторный запрос старым токеном | держим не дольше `SABY_TOKEN_TTL_SECONDS` (1 ч) — консервативно и безопасно |
| `pageSize` больше максимума не отвергается (101 → HTTP 200) | `pageSize=101` | всё равно просим ≤ 100: лишнего API не отдаст |
| Ограничения на длину периода не обнаружено | выборка за 9 месяцев — 0,6 с | синкаем диапазоном, как на iiko |
| `toDateTime` можно не передавать | запрос только с `fromDateTime` | передаём всегда — так выборка предсказуема |
| Методов записи номенклатуры в Retail/Presto API **нет** | разделы `app_sale`/`app_presto` целиком | блюда и меню заводятся только в кабинете |
| `POST /retail/order/create` — это заказ **на доставку** (`product=delivery`), а не кассовая продажа | документация метода + пустое тело → HTTP 500 | не используем: в кассу не пишем, а фискальный чек API не пробивает вообще |

Отдельно про синк: **пустой ответ кассы поверх непустого дня в БД считается сбоем выборки**
и данные не затираются (`sync_orders_range`), а дни раньше `POS_SWITCH_DATE` синк не трогает
вовсе — иначе первый же синк после переезда стёр бы историю iiko, которой больше нигде нет.

## Чего в Saby API НЕТ (проверено по документации всех разделов)

1. **Агрегатов и отчётов.** Нет аналога `POST /api/kpi/dashboard/get-data` (метрики
   выручки/чеков/среднего чека) и нет OLAP-движка. Есть только выгрузка продаж.
   Разделы «Отчетность» и ОФД — про налоги и фискальные чеки, не про аналитику.
2. **Типа обслуживания** в продаже (зал / с собой / доставка).
3. **Числа гостей**, **номера стола**, **зала** в продаже (зал есть в карточке точки,
   но `halls` у нас пуст).
4. **Имени кассира** — только `Teller` (id).
5. **Категории номенклатуры** в позиции продажи — только id, категория из каталога.
6. Фильтра по `Updated` в `order/list` — инкрементальный синк «по изменённым» не выйдет,
   только по датам продаж.

## Покрытие: что было в iiko и что будет в Saby

Таблица по каждому источнику данных, который сегодня использует дашборд и табло.

| Что нужно | iiko сегодня | Saby | Итог |
|---|---|---|---|
| Заказы: номер, время открытия/закрытия | OLAP `OrderNum`/`OpenTime`/`CloseTime` | `Number`, `OpenedWTZ`, `ClosedWTZ` | ✅ равноценно |
| Позиции чека: имя, кол-во, сумма | OLAP `DishName`/`DishAmountInt`/`DishSumInt` | `SaleNomenclatures[]` | ✅ равноценно |
| Категория блюда | в ответе `get-data` (`decoration.product`) | отдельный запрос каталога + join по id | ⚠️ работает, но **зависит от того, как заведены папки меню** |
| Тип позиции (блюдо/товар/модификатор) | `productType` из `get-data` | `IsModifier` + корневая папка каталога | ✅ **лучше**: флаг модификатора приходит в самой продаже |
| Себестоимость позиции | `ProductCostBase` (в iiko не заполнена → food cost сломан) | `PlannedCost` (ТТК) + `TotalCost` (склад) | ✅ **лучше**, если завести ТТК в Saby |
| Скидки | метрика = 0 (скидок нет) | `TotalDiscount` + `DiscountInfo[]` | ✅ равноценно |
| Оплаты (нал/карта/сплит) | OLAP `PayTypes`, сплит строками | `Payments[]` с `CashSum`/`BankSum`/`BankType` | ✅ **лучше**: структура нативная |
| Кассовая смена | OLAP `SessionNum` | `ShiftNumber` | ✅ равноценно |
| Кассир | OLAP `Cashier` (имя) | `Teller` (**только id**) | ✅ не важно: **ни один экран и ни один эндпоинт кассира не читает** (проверено grep'ом по backend и frontend) |
| Выручка/чеки/ср. чек по дням | метрики `REV_GROSS`/`TRN_ALL`/`AVERAGE_SPEND_GROSS` | считаем сами из заказов | ✅ равноценно (уже считаем из БД) |
| Выручка по часам | `DATA_SUMMARY_BY_HOURS` | считаем сами из заказов | ✅ равноценно |
| Дейпарты, свод по дням недели, ОП-отчёт, план | производные от часов/заказов | то же | ✅ равноценно |
| Меню-инжиниринг, ABC, состав чека, сочетаемость | OLAP по заказам | то же из заказов | ✅ равноценно |
| **Канал: в зале / с собой** | модификатор категории «Статус» в заказе | системного поля нет, **но схему можно повторить**: папка «Статус» в меню Presto с позициями по 0 ₽ — адаптер их читает (`SabyPos._channel`) | ⚠️ **зависит от настройки меню**: заведём «Статус» — разрез сохранится полностью; не заведём — всё станет «в зале» |
| **Гости, ср. чек на гостя** | OLAP `GuestNum` | поля нет → адаптер ставит **1 гостя на чек** | ✅ цифры не меняются: у этой точки кассир гостей не вводит, и iiko отдаёт ровно 1:1 к чекам (проверено на боевой базе, август 2026) |
| Стол, зал | OLAP `TableNum`/`RestaurantSection` (у фастфуда и так пусты) | нет (залы не настроены) | ⚠️ де-факто не теряем |
| Возвраты | метрика `REFUND_TRN` | `Return` у продажи | ✅ равноценно |
| **История продаж до переезда** | вся история в iiko | Saby знает только свои продажи | ❌ **iiko-историю надо выкачать в нашу БД ДО отключения iiko** |
| Табло: заказы за сегодня | живой OLAP, ответ за секунды | `order/list` за сегодня (или вебхук) | ✅ равноценно, вебхук даже быстрее |

Итог: **по продажам и деньгам Saby покрывает все наши потребности** и местами лучше iiko
(себестоимость позиции, оплаты, модификаторы). Из трёх «потерь» две закрыты в адаптере
(гости = 1 на чек — ровно как сейчас; кассир нигде не используется), третья —
**в зале / с собой** — закрывается настройкой меню: папка «Статус» с тремя позициями по
0 ₽, как это уже сделано в iiko. Единственная неустранимая вещь — **история продаж до
переезда: её надо сохранить в нашей БД, Saby её не отдаст**.

## Что дала публичная документация, а что — нет

Проверено 25.09.2026: прочитаны все разделы API (`app_sale`, `app_presto`, `auth`,
`trigger`, `inventory`, оглавление всех 20 групп), страница продаж разобрана целиком —
включая полный перечень полей, который на самой странице отрисован таблицей.

| Вопрос | Ответ документации |
|---|---|
| Полный список полей продажи/позиции/оплаты | ✅ **есть**, выписан выше целиком |
| Тип обслуживания, гости, стол, зал в продаже | ✅ ответ есть и он отрицательный: **таких полей в ответе нет** |
| Как приходят модификаторы | ✅ `IsModifier` + `Positions[]` («массив дочерних позиций») — разбираем оба случая |
| Себестоимость | ✅ `PlannedCost` (плановая) и `TotalCost` (фактическая) |
| `TotalPrice` — до или после скидки | ❌ **не сказано**: рядом есть `CheckSum`, `CheckPrice`, `CatalogPrice`, `TotalDiscount`, а какая из сумм со скидкой — не описано |
| Формат номера продажи | ❌ сказано только «string» |
| Заполняется ли `PlannedCost` без ТТК | ❌ не описано |
| TTL и обновление токена | ❌ не описано (в ответе живьём есть `access_token`/`sid`/`token`) |
| Лимиты частоты запросов | ❌ не описано; известно лишь `pageSize ≤ 100` |
| Формат и гарантии вебхука | ❌ не описано — тело и заголовки задаём мы сами в конструкторе триггера; про повторы и подтверждение ни слова |
| Пример JSON-ответа | ❌ на странице только примеры **запроса** (PHP/cURL, Python/requests); «Скачать пример» подгружается скриптом и в исходнике страницы отсутствует |

Итого: три вопроса из семи документация закрыла, остальные — только живым чеком.
Ожидания зафиксированы в `backend/tests/test_pos_saby.py` (фикстура собрана по
документации, не с кассы) — сверить, когда появится первая продажа:

1. `TotalPrice` позиции — до или после скидки (мы считаем «после», брутто =
   `TotalPrice + TotalDiscount`). У точки скидок нет, так что цифры совпадут при любом
   ответе, но правило лучше знать точно.
2. Формат **номера продажи** (сквозной за смену? с префиксом? буквы?) — от этого зависит
   миграция схемы табло (`orders.number INTEGER` → текст).
3. `PlannedCost` без заведённых ТТК (ожидаем 0) и `TotalCost` без складских документов.
4. **Сквозной ли номер продажи** или он, как в iiko, начинается заново каждый день. У нас
   ключ заказа всегда пара (дата, номер), так что оба варианта работают, но знать полезно.
5. Приходят ли **недокументированные** поля (тип обслуживания, гости, стол): Presto
   ресторанный, и в живом `point/list` уже нашлись `halls`, `paymentKinds`,
   `deliverySettings`, которых в документации нет — значит и в продаже может быть больше.
6. Пагинация на большом дне (>100 чеков) и работа `hasMore`.
7. Что в `Payments[].BankType` при оплате через агрегатор, если она появится.

Ещё одна лазейка, которую видно только в кабинете: **в конструкторе триггера** («Изменения
информации о продажах») список доступных полей продажи может быть шире, чем в `order/list`.
Если тип обслуживания есть там — канал можно получать вебхуком без служебных позиций.

### Что код уже переживает сам (26.09.2026)

Часть белых пятен закрыта не ожиданием чека, а тем, что адаптер принимает **любой** из
вариантов. Каждый случай — отдельный тест в `test_pos_saby.py`.

| Неизвестное | Как держит адаптер |
|---|---|
| Формат `*WTZ`: с поясом или без, в каком поясе | оба вида; смещение переводится в `settings.timezone`, в БД — наивное время точки, как у iiko |
| Страницы с 0 или с 1 | записи склеиваются без повторов по `Sale`/`Key`/`id`; повтор страницы 0 на странице 1 допускается, повтор дальше останавливает цикл |
| Совпадают ли `Nomenclature` продажи и `id` каталога v2 | каталог индексируется и по `id`, и по `externalId` ↔ `NomenclatureUUID` |
| Платёж без разбивки нал/безнал (агрегатор) | сумма `Amount` уходит в «Прочее», Σ оплат = выручке |
| «Статус» заведён модификатором и в каталог не попал | строка по 0 ₽ с именем «В зале»/«С собой»/«Доставка» считается служебной: канал найден, в позиции чека не идёт |

Живой чек по-прежнему нужен для остального: скидка в `TotalPrice`, формат номера,
`PlannedCost` без ТТК, недокументированные поля, задержка появления чека в API.

## Сверка документации 26.09.2026

Перечитаны `saby.ru/help/integration/api` (оглавление, 20 групп) и
`…/api/app_presto` целиком. Нового для продаж и аналитики нет: методы чтения продаж
живут только в `app_sale` (`order/list`), а `app_presto` — это доставка, бронь столов,
бонусы и вебхуки. Что нашлось и чем может пригодиться:

| Метод | Что даёт | Нужно ли нам |
|---|---|---|
| `GET /retail/nomenclature/stop-list` (`pointId`, `page`, `pageSize`) → `id`, `name`, `balance`, `count`, `period` (ч), `reason`, `stopListId` | позиции в стоп-листе | не сейчас; задел под «что закончилось» на табло или в дашборде |
| Presto «Бронь»: точка, меню, список блюд, **список столиков**, время брони | столы и залы для брони | нет: у фастфуда столов нет, в продаже стол всё равно не приходит |
| Presto «Вебхуки» | тот же триггер «Изменения информации о продажах» из кабинета; формат тела и гарантии доставки по-прежнему не описаны | только если задержка опроса окажется большой для табло |
| `inventory` (склад) | карточки складов и ЭДО-документы; **ТТК, себестоимости и остатков по API нет** | нет |

Меню, ТТК и поставщиков в Saby заводит шеф-повар Дима — с нашей стороны это не задача.
Когда ТТК будут заведены, `PlannedCost` в продаже должен дать food cost по кассе: это
проверить на живом чеке (пункт 3 списка выше).

## Действия в кабинете Saby (нужны от владельца)

API-методов записи в Saby Retail/Presto для этих задач нет (только чтение), и права нашего
приложения — «Просмотр». Значит всё это делается руками в кабинете.

1. **Завести меню** (сейчас позиций 0): структура папок внутри «Блюда» = наши
   меню-категории (Дюрюмы, Напитки, Комбо, Допы и соусы…). Вложенность до 3 уровней.
   Категории дашборда берутся именно оттуда — как назовём папки, так и будет в отчётах.
2. **Завести папку «Статус»** с тремя позициями по 0 ₽: «В зале», «С собой», «Доставка» —
   тот же приём, что уже работает в iiko. Кассир отмечает канал, и разрез «в зале /
   с собой» (сейчас 36 % / 64 %) переезжает без потерь. Код это уже поддерживает.
3. **Поправить режим работы точки**: 12:00–22:00 **ежедневно** (сейчас 12–22 пн–пт, сб/вс
   выходные). Путь: Настройки → Точки продаж → карточка точки → режим работы.
4. **Завести ТТК** (шеф-повар Дима, в работе) — тогда `PlannedCost` даст настоящий food cost по кассе; сейчас
   он сломан, потому что в iiko себестоимость не заполнена.
5. **Пробить один-два тестовых чека** (хоть на 10 ₽: обычный и со сплит-оплатой) — это
   единственный способ закрыть список белых пятен выше. Сами мы это сделать не можем:
   API не создаёт ни блюда (методов записи номенклатуры нет), ни кассовую продажу
   (`order/create` — это заказ на доставку, а у точки доставка выключена), а фискальный
   чек печатает ККТ, не API. Как только чек появится — весь путь по API проверяется за
   минуту.
6. **Заглянуть в конструктор триггера** «Изменения информации о продажах» и посмотреть,
   есть ли в списке доступных полей тип обслуживания.
